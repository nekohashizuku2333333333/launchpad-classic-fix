# 内存、选中反馈与拖动排序修复

研究与验证日期：2026-09-22。目标是解决隐藏后内存不下降、图标外的大白框，以及排序时跳位和跨行生硬的问题。本机运行 macOS 26.6.2；这里记录本项目的实现与实测，不将其称为 Sequoia 15 原版的逐帧验证。原版视觉依据另见 [Sequoia 参考记录](sequoia-reference.md)。

## 依据与诊断

[Apple 的内存优化指导](https://developer.apple.com/documentation/xcode/making-changes-to-reduce-memory-use)建议按显示用途缩小图像、释放不再使用的视图资源，并在返回前台时重新准备。本项目原先隐藏窗口时仅使内容透明：背景 loader 字典虽然清空，`selectedBackgroundImage` 仍持有同一像素数据；图标缓存与挂载的 `ApplicationArtworkState` 也继续持有图像。这是可达对象的保留，不能仅凭占用偏高认定为不可达内存泄漏。

[Apple 的 SwiftUI identity 说明](https://developer.apple.com/videos/play/wwdc2021/10022/)解释了视图身份如何影响状态寿命与移动动画。原先各行分别建立 `ForEach`，同一 app 跨行时会进入另一个身份范围，容易表现为旧图标消失、新图标出现；这与本次排序的跳变原因相符。

## 已实现的调整

- 隐藏后卸载图标和背景视图，释放各图标状态中的 `NSImage`；清空模型持有的背景图像和图标缓存，再按顺序清理图标 loader 缓存。资源代次和任务取消检查阻止旧请求回填。背景 loader 保留至多一张已缩小的 RGBA 数据，成本不超过9 MiB，避免每次重新打开都解码原始大图。
- 再次显示前，`prepareForPresentation()` 等待清理结束，预载即将显示的当前页，从有界背景缓存准备壁纸，再呈现窗口。磁盘图标缓存仍保留，避免每次重新解析应用图标。
- 模糊壁纸的解码最大边由 3072 改为 1536；最大 RGBA 缓冲为 `1536 × 1536 × 4 = 9 MiB`，16:9 图片约为 5.06 MiB。相同纵横比的像素缓冲减少 75%，这不是整个应用内存减少 75%。背景仍使用原有模糊效果，没有引入新的 GPU 预模糊缓存。
- 图标正规化与背景解码用局部 `autoreleasepool` 及时释放临时 AppKit/ImageIO 对象；背景仅将包含 RGBA `Data` 的结果带出作用域。取消的加载请求不会从缓存继续返回图像。
- 移除选中反馈的白色描边，将淡色底板缩至 `iconSize × 0.8 + 10`，贴合可见图标主体。鼠标打开项目与键盘选择分离，保留方向键和搜索首项所需的反馈。
- 根页与文件夹改为同一页内的平铺身份范围，以稳定的项目 ID 移动坐标。拖起时先保留原槽空位，悬停潜在文件夹目标或短暂离开网格时保留有效插入空位，避免网格反复收缩展开；实际顺序仍在有效 drop 时提交。
- 普通排序使用响应时间 0.26 秒、阻尼比 1 的弹簧；减少动画模式使用 0.14 秒无回弹缓动，保留短暂且可跟踪的让位反馈。参数是本项目针对反馈的调整值，不是公开的 Sequoia 内部参数。

## 同条件内存测量

使用独立 `Launchpad Classic Debug.app` 与隔离偏好设置，未更改正式应用的用户布局。以下采用 `footprint PID` 的 `phys_footprint`，单位保留工具输出的 MB；不能与 `ps` 的 RSS 或虚拟地址空间大小直接比较。

| 操作状态 | 修改前 PID 15483 | 最终构建 PID 17104 |
| --- | ---: | ---: |
| 初次显示 | 91 MB | 64 MB |
| 翻到第 5 页 | 91 MB | 78 MB |
| 隐藏 | 92 MB | 59 MB |
| 重开并隐藏 3 次后 | 92 MB | 65 MB |
| 上述流程中的峰值 | 103 MB | 81 MB |

最终构建的首页占用下降约30%，三次开关后后台占用下降约29%，该流程峰值下降约21%。这些是同机单轮对照结果，不是所有应用数量、壁纸或显示配置的固定值。表中统一使用辅助数据里的 `phys_footprint`；`retained-cycles-hidden.txt` 的标题因取样/取整显示64 MB，辅助字段显示65 MB，表中取后者。

原始记录位于 `.build/memory-study/` 的 `before-` 与 `retained-` 开头文件，各自包含 `visible`、`pages`、`hidden`、`cycles-hidden` 四种状态。过程中曾测试每次隐藏都清除背景缓存：常驻量下降，但重新解码原图使重复打开峰值达到113–118 MB；加入局部 `autoreleasepool` 也未消除此问题。因此最终保留单张最多9 MiB的缩小背景缓存，避免反复解码。`after-` 与 `final-` 开头文件属于中间实验，不作为交付构建的结果。

首轮隐藏后的只读 `heap -s --noContent` 摘要未列出 `ApplicationArtworkState` 实例；仍有32个 `NSImage`、31个 `NSBitmapImageRep` 和 SwiftUI 的显示缓存字典。`footprint` 中剩余 ImageIO 项标为可回收。它们可能来自系统渲染缓存，摘要无法确定引用链，因此没有直接禁用 `NSImage.cacheMode`，也没有把它们定性为泄漏。完整摘要保存在 `after-hidden-heap.txt`。

复测须保持相同屏幕、壁纸、应用列表和操作顺序；不将理论像素缓冲变化代替进程实测，也不将一轮测试视为长期无增长的证明。

## 验证状态

最终完整质量测试 **96/96 通过**，包含四组新增排序连续性回归及隐藏释放、重新预载的生命周期检查。其中新增 `MemoryResourceTests` 独立运行 **3/3 通过**：4096×2304 图像缩至1536×864，重建的 `NSImage` 保持该分辨率且像素非空；3200×3200 图像缩至1536×1536，实际像素成本不超过9 MiB；取消请求不能取回已缓存的背景。测试只生成临时图像，不启动应用。

本机「减少动画」开启（`reduceMotion = 1`）时，原生 GUI 已通过以下操作：鼠标打开并关闭文件夹后不残留选中框；键盘选择仍有淡色反馈；根页 Audio MIDI Setup 跨行排序；文件夹内 Bluetooth 跨行排序；文件夹成员拖出后插入根页第三个位置。测试后已恢复调试副本的应用列表与排序基线。上述结果验证指定操作，不替代动画帧率量测或与 Sequoia 的逐帧对照。

最终 Universal 2 构建包含 arm64 与 x86_64，`codesign --verify --deep --strict` 通过。最终缓存策略下连续三次重新打开均正常；再次打开后直接输入 `terminal`，搜索和淡色首项提示正常。调试副本已退出。普通动画模式的曲线已实现，但本轮没有另行切换系统设置做 GUI 对照，也没有采集 FPS 或帧时间。
